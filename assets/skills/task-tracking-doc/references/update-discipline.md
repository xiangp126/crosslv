# 更新契约与证据规则(完整版)

`SKILL.md` §4 是摘要。这里是展开版,以及本文体真正的门槛 —— 证据规则。

## 1. 为什么"定期更新"一定失败

定期更新要求在"没有触发信号"的时刻想起一件事。人和 agent 都做不到。
**只有事件驱动能活下来**:动作本身就是信号。

所以契约写成 **一个动作 = 执行 + 落账**,而不是"记得更新文档"。
没落账的动作**视为未完成**,不进入下一步 —— 这一条是整套纪律的地基。

这条规则最早的形态是 2026-04 一份性能二分模板里的英文段落:

> The report must be updated live, not as a post-processing step.
> After every single test run, record: … **Do not proceed to the next test until the
> current result is documented.**

三份互不相干的真实文档后来各自独立长出了同一条规则(中文版),这不是巧合。

## 2. 七类事件,以及为什么是"至少要落这些字段"

字段不是随便定的,每一个都对应一次真实的返工。

| 事件 | 至少要落 | 少了会怎样 |
|---|---|---|
| 长命令 / build 结束 | 结果、耗时、`error:` 数、**日志路径** | 事后只记得"跑过了",不知道跑的是哪一版 |
| push 完成 | change 号、**新 patchset 号**、服务器回显 | 下次 rebase 拿错 patchset,覆盖掉别人几轮修改 |
| CI 出结果 | build 号、失败 stage、下游作业号、**session id** | console 有保留期,过期后只能从代码倒推 |
| merge / 落地 | 时间、**落地后真实 SHA** | 合入常被 rebase,推上去的 SHA 在分支上根本不存在,查无此物 |
| 评审意见 | 谁提的、文件行、怎么改的 | 同一条意见被提第二次时说不清上次怎么处理的 |
| 实验结果 | 配置、种子、**对照组**、VERDICT | 没有对照的实验结果不能用于归因,等于白跑 |
| **判断被推翻** | 就地写「⚠ 更正」,不删旧结论 | 同一个错误结论会被第二次、第三次重新推导出来 |
| session 被打断 | 在途项 + 下一步 | 下次开场要花十几分钟重建上下文 |

## 3. 两条配套

**日志先落盘再说结论。** 归档都有保留期(CI console 约 12 天;失败数据库约 8 天;
测试归档约 12 天)。**在窗口内不落盘 = 永久丢失。** 先 `curl`/`cp` 到 `logs/`,
再开始分析。

**标识符写全,并注明种类。** 至少区分这三种,它们长得一样但值不同:
- 推送之前的**本地 SHA**
- 代码评审系统上的 **patchset revision**
- 合入之后**分支上的真实 SHA**

只写一个裸 hash 而不说是哪种,后面查证时会得出"这个 commit 不存在"的错误结论。

## 4. 证据规则 ★

这是本文体区别于普通工作日志的地方。**记录不等于证明。**

### 4.1 每个结论必须指得到一条对照

零命中不是证据,除非同时有一个**已知存在**的对照也用同一方法查过。

真实案例:用 `--errlike "0xac5816"` 查失败数据库得到零行,差点据此判定"这个失败在历史上
不存在"。跑了对照关键词(已知有大量记录)**同样零行** —— 于是发现是工具路径过期,
库根本没数据。没有对照行,这个错误结论会直接进入对外答复。

写进表里:

```markdown
| **对照:<已知存在的东西>(证明查法有效)** | 10 处 | 8 处 | 8 处 |
```

### 4.2 判据至少跑两条,不一致以最底层的为准

查"某改动在不在某分支上",三条判据:
1. 标识符(Change-Id 之类)—— **最弱**,传播时可能被换过
2. 标题 / subject —— 中等,可能被改写
3. **代码内容** —— 最强,内容不会说谎

真实案例:只用 Change-Id 查,得出"C0/C1 只在 master"的结论;改用 subject 判据才发现
它们在其他分支用的是**另一套 Change-Id**,四轨其实都有。

⚠ **`git merge-base --is-ancestor <hash> <branch>` 在 cherry-pick 的世界里恒定不可用** ——
跨分支传播会换 hash。这个坑踩过不止一次。

### 4.3 "没证伪" ≠ "成立"

没有找到反例,只说明没找到。在拿到正面证据之前,结论标 `🟡 未证实`,
**不要用于对外答复**。

### 4.4 归属裁决要"内容证据 + 时间线证据"双跑

- 内容证据:代码路径上到底经不经过我们的改动
- 时间线证据:失败首次出现的时间 vs 改动落地的时间

⚠ 时间线证据有个陷阱:**失败数据库的保留期会伪造"首次出现"**。
看到"从 X 日开始出现"时,先确认 X 日在保留窗口内部,否则那只是窗口边界。

### 4.5 排除法要把每个假设都写出来并给实测

```markdown
| 假设 | 结论 |
|---|---|
| <假设一> | ❌ **证伪** —— <实测证据> |
```

被证伪的假设**留在表里**。下一个人(或下一个 session 的自己)会想到同一个假设,
表里写着就不用再试一遍。

## 5. 元规则

### 5.1 不信任本文档自身

文档里记的 patchset 号、分支 tip、票状态都是**写入当刻的快照**,天然会过期。

真实案例:照文档里记的 "PS19" 直接取来 rebase,实际当天已经推到 PS24,
中间被精简掉 84 行 —— 差点覆盖掉五个 patchset 的修改。

**固定流程:动手前重查线上系统,拿到的值和文档不一致时,以线上为准并就地更正文档。**

### 5.2 文档写"作废"必须同刻在线上执行

写了"已作废"但没在系统里 abandon,两边对不上,是自欺。
**处置动作和记录动作要在同一批完成。**

### 5.3 诊断与处置分离

诊断可以自己做完。**落码 / 推送 / 改线上状态 / 发对外消息一律先报方案拿指令。**
未执行的方案写在 `#### 处置建议(未执行,等指令)` 下面,不要混进已完成的记录里。

### 5.4 已知违规实例也登记,并标明"它不是范例"

发现某条历史记录不符合现在的规矩(比如缺了必须的 footer),而它已经无法修改时,
**把它登记下来并显式写"它不是范例"**。否则下一个人会照着它学。

### 5.5 编号只增不重排

发布过的章节号不再重排。新增用插入式编号:`1.5` / `4.16` / `7bis` / `7ter` / `7quater`。
原因很简单:`见 §4.19` 这类交叉引用一旦失效,**比没有引用更糟** —— 它会静默指向别的内容。

## 6. 什么时候该分拆子文档

`TRACKING.md` 会长。到几千行是正常的,**不要因为长就拆**。

该拆的信号只有一个:**某块内容自成体系,且会被独立引用**
(例如一份代码流程说明、一份交接文档、一次独立调查的完整过程)。

拆出去的子文档:
- 用小写描述性文件名
- **必须登记进 `TRACKING.md` 的姊妹文档表**
- 在 `TRACKING.md` 里留一行摘要 + 指针,不要只留指针

不该拆的:按时间分卷(`TRACKING_2026Q3.md`)、按状态分卷(`TRACKING_done.md`)。
这两种拆法会让"查一件事的完整经过"变成跨文件考古。
